# Skill selection probe

Generated by `python -m evals.selection --write` from every SKILL.md. Do not
edit by hand.

You are choosing which skill to load for the user's message. A host gives you
only these names and descriptions. Do not carry out the request and do not ask
a question. Reply with exactly one line: `Skill: <name>` for the one skill whose
description fits the message best, or `Skill: none` when none fits.

## Skills

- `mastermind-agent-handoff`: Use for ordinary in-session research, implementation and review handoffs. Not for rewriting the request itself (use mastermind-prompt-refiner). Routes effort and carries bounded context before every new agent in a Mastermind workflow.
- `mastermind-agent-security-review`: Use for a security review or a change touching auth, secrets, tool execution, delegation or prompt injection. Not for mapping reach before design (use mastermind-security-research). Evidence-based review of agent tools, permissions, untrusted input, supply chain.
- `mastermind-architecture-review`: Use for service boundaries, async workflows, persistence, migrations, public APIs, events and schemas. Not for a line-level diff review (use mastermind-diff-review). Checks the runtime path, ownership, retries, idempotency and compatibility.
- `mastermind-audit-attestation`: Use to generate, verify, sign or explain Mastermind audit envelopes and GitHub attestations. Not for reviewing the audited code (use mastermind-diff-review). Tampering checks, Ed25519 signatures, CI provenance, integrity versus signer trust.
- `mastermind-browser-verification`: Use after a UI change in a client that can drive a browser. Not for a code review of components (use mastermind-frontend-audit). Records evidence: accessibility tree, console and network errors as failures, viewport and colour-scheme checks.
- `mastermind-change-impact`: Use before editing, while planning or in PR review to see what a change touches since a git ref. Not for choosing tests (use mastermind-test-impact). Brief from `mastermind impact`: changed symbols, callers, API crossings, collision risk.
- `mastermind-codegraph-research`: Use whenever a task needs a structural fact, before Bash or text search. Not for an architecture briefing (use mastermind-project-map). Answers with mmcg: symbols from plain terms, existence, callers, callees, imports, blast radius, staleness.
- `mastermind-comment-audit`: Use when asked to check code comments or when a finished diff changed comments. Not for writing code (use no-ai-slop-comments). Read-only: flags narration with evidence, names what it kept, reports removed rationale.
- `mastermind-component-research`: Use before creating or changing a React or Vue component, or for "build this screen". Not for a design handoff (use mastermind-design-intake). Checks in the codegraph whether the component exists, who renders it and its props.
- `mastermind-critical-review`: Use before drafting a sensitive spec or approving a plan, or when a critic or auditor needs a rubric. Not for a code diff (use mastermind-diff-review). Stress-tests designs, specs, plans and reports for false assumptions and missing evidence.
- `mastermind-cross-client-setup`: Use when installing Mastermind in Claude Code, Cursor, Codex, Continue or another client, or fixing its MCP setup. Not for using Mastermind once installed. Covers project or user scope, previews, updates, removal and doctor checks.
- `mastermind-dependency-upgrade`: Use for version bumps, Dependabot or Renovate PRs, lockfiles, new packages and unused ones. Not for one vulnerability alert (use mastermind-scanner-alert-response). Smallest compatible change, vets new package names, keeps install scripts off.
- `mastermind-design-intake`: Use when a Figma frame, mockup or design spec is handed over for implementation. Not for whether a component exists (use mastermind-component-research). Writes a checkable task contract: named source, resolved components, tokens, unverifiable items.
- `mastermind-diff-review`: Use when asked to review code, a PR, a branch or a follow-up push, or whether it is safe to merge. Not for a design with no code yet (use mastermind-critical-review). Read-only, safe for forks: broken callers, unchecked input, lost errors, races, CI permissions, hidden text.
- `mastermind-docs-authoring`: Use when asked to write, update or review docs, fix stale docs or record a decision. Not for code comments (use no-ai-slop-comments). Keeps every command, flag, path and claim in READMEs, guides, runbooks and diagrams true of the code.
- `mastermind-frontend-audit`: Use after a React or Vue change or for "review this UI change". Not for checking the page in a browser (use mastermind-browser-verification). Read-only: unrendered components, props changed without callers, reinvented components, raw values over tokens.
- `mastermind-investigation-ledger`: Use when something is broken with no supported cause, has several plausible causes or changed between versions. Not for a failed CI job or a known cause (use mastermind-verify-change). Reproduces, bisects and tests competing hypotheses before a fix.
- `mastermind-product-intake`: Use when a PRD, ticket or feature request is handed over for implementation. Not for a design file or mockup (use mastermind-design-intake). Writes a task contract that can fail: behaviour over outcome, nouns mapped to symbols, gaps as questions.
- `mastermind-project-history`: Use when asking why a design exists, whether an approach was tried or what supersedes a decision. Not for current code structure (use mastermind-codegraph-research). Reasons from recorded decisions and lessons without treating rank as proof.
- `mastermind-project-map`: Use when exploring an unfamiliar repository. Not for one symbol's callers or impact (use mastermind-codegraph-research). Briefing from `mastermind map`: components, entry points, reading order, cycles, hotspots and precision limits.
- `mastermind-prompt-refiner`: Use when asked to improve or rewrite a prompt, or before handing a rough request to a cold agent. Not for a request that is only informal or long. Rewrites the request for another agent and keeps the original verbatim.
- `mastermind-runtime-research`: Use before changing an API, queue consumer, background job, migration or shared state. Not for judging the design (use mastermind-architecture-review). Finds who depends on it and the runtime links the codegraph cannot span.
- `mastermind-scanner-alert-response`: Use to look into, fix, assess or close a Dependabot, CodeQL or secret-scanning alert. Not for a general security review (use mastermind-agent-security-review). Works one alert to a verified fix or disposition without reading a secret's value.
- `mastermind-security-research`: Use before designing an auth, permission or secrets change. Not for a security verdict (use mastermind-agent-security-review). Lists what the change can reach and what enforces it: privileged operations, callers, guards, secret readers, gaps.
- `mastermind-structured-report-contract`: Use for executor evidence, schema-v1 report validation, controller audit inputs or strict auditor output. Not for executing the task (use mastermind-task-executor). The file-backed executor report parsed by `run-task --post-only`.
- `mastermind-style-deep`: Use for "deep style", "design patterns" or "qualitative profile" requests. Not for repository conventions, which always win. Drafts how the author develops from attributed code and commits, a candidate until the author verifies it.
- `mastermind-task-executor`: Use when handed a `.mastermind/tasks/<NNN>-<name>/spec.md` or asked to execute an approved task. Not for work without an approved spec (use mastermind-task-planning). Works within Scope, proves the criteria, writes the executor report.
- `mastermind-task-planning`: Use when starting or scoping non-trivial repository work. Not for executing an approved spec (use mastermind-task-executor). Picks the lightest workflow for the risk and writes a task contract when one is needed.
- `mastermind-test-audit`: Use after implementation or when a change claims test coverage. Not for choosing which tests to run (use mastermind-test-impact). Read-only check that tests prove the change: unreached code, wrong path, moved assertions, empty tests, likely surviving bugs.
- `mastermind-test-impact`: Use when deciding which tests to run first for a change. Not for judging whether tests prove it (use mastermind-test-audit). Ordered plan from `mastermind impact`: direct, transitive and heuristic candidates before the full gate.
- `mastermind-verify-change`: Use to verify, test or smoke-test a change or PR, explain a red CI run or show it is ready. Not for a bug with an unknown cause (use mastermind-investigation-ledger). Gates untrusted code, then runs the smallest checks that prove the change.
- `no-ai-slop-comments`: Use when writing or editing code, applying a spec, or when told "stop adding comments". Not for auditing a finished diff's comments (use mastermind-comment-audit). Keeps comments that explain why, deletes ones that restate the code.
